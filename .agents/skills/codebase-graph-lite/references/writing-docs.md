# 文件寫作指引

對話提供素材。替沒參與討論、可能半年後才讀到文件的人重寫，讓他們能從文件本身理解現況與決定的理由。這份指引適用於本技能產出的架構圖、README、規格、交接文件、決策紀錄、PR／MR 描述、議題和維護手冊。

## 下筆前

1. **確認放在哪裡。** 每項資訊選一處作為主要維護來源。其他文件只放讀者需要的摘要及連結。
2. **查證現況。** 實作行為以程式碼為準，部署事實以可查證的環境設定或執行證據為準。若使用者的描述和程式碼、文件或設定衝突，先在對話中指出差異。若規格和實作不一致，分別寫出預期行為及現況，保留差異供後續判斷。
3. **分清事實與判斷。** 寫明已驗證的事實及已做的決定。重要但未驗證的內容，標「未確認」並附上確認方式。把偏好寫成採取某做法的理由。

## 把對話改寫成文件

| 對話素材 | 文件寫法 |
| --- | --- |
| 口語、情緒 | 寫具體的問題、狀態或影響。 |
| 「照你說的」「如前述」 | 直接寫結論及讀者需要的背景。 |
| 「原本」「現在」「新版」 | README、wiki、手冊描述目前行為。PR／MR、變更紀錄、決策紀錄依用途保留歷程。 |
| 來回澄清的問答 | 保留讀者也會遇到的疑問及答案。 |
| 臨時代號或編號 | 寫出方案內容。引用既有議題或決策時附標題。 |
| 「注意」「務必」 | 說明漏做哪件事會出現什麼症狀。 |
| 誰提議或核可 | 會議紀錄依用途保留歸屬。其他文件寫決定內容及技術理由。 |

交接文件與決策紀錄先給結論和接手需要的細節。團隊文件採中性語氣。跨團隊或對外文件採正式語氣，寫本方能確認的內容。

## 交出前

用讀者的身分讀一遍。確認文件離開對話仍讀得懂，必要的理由和驗證方式有保留，簡單的想法也沒有被擴寫成一套新制度。若任務包含功能收尾並準備提交 PR／MR，依[維護手冊指引](maintenance-manual.md)完成手冊後再提交。
